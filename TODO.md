## Heuristics

Ways to make split detection's recognition of deaths, game overs, resets, star and key grabs, fadeouts and fade-ins more accurate, ranked by what pays off most, with the cheap and deterministic ones before the learned ones. Today it polls at 6 to 29.97 fps depending on the process, times events when it looks at a frame, not when the frame was captured, and decides from hand-tuned colour and template checks on small regions.

1. **Score detection against labelled events.** The traces in `tests/recordings/traces` only show that a change leaves detection the same, not that it's right. Label each recording's events frame-accurately (fadeout, fade-in, death, star grab, key grab, reset, Grand Star), and score detection per event type for precision, recall and timing error. This shows which events are weak, and every item below needs it to be shown to help. `tests/score.py` scores a replay against the labels in `tests/recordings/events`, `tests/label.py` pre-labels a recording from what detection did and draws frames around each event to correct them by eye, and the Grand Star is labelled for the six ending recordings. What's left is reviewing the labels of the full runs (the pre-labels of greensuigi's are generated, with `"reviewed": false`), and adding what detection never logs: deaths, key grabs, and the fadeouts and fade-ins it doesn't count. Detection has no key grab event at all yet, so it scores as all misses.

2. **Separate perception from decision.** Run a perception step on every captured frame, with that frame's own timestamp: fade level from 0 to 1, HUD present, reset logo score, star digits, power meter, X-Cam, scene. A temporal event layer (an HMM or state machine with hysteresis) then turns that stream into events, and can confirm them with a few frames of hindsight. This fixes events missed between looks, wall-clock timing, and the `time.sleep` calls in processes (final star, file select) that leave frames unseen. It needs no ML, so it can land first and keep the traces the same. Also:
   - Make events edges, comparing a frame's perception with the previous frame's, as fmichea's ASL autosplitter does with memory values, instead of level checks patched with `split_cooldown`, `_split_on_current_xcam` and fade count resets.
   - Read frames on their own thread into a bounded queue, as pilgrim-autosplitter does, so nothing sleeps while frames go unseen.
   - Unit-test each rule on synthetic perception sequences, as fmichea's ASL does on mock memory states, which is faster and more precise than a recording per rule.
   - kainev's AutoSplit64 v2 went this way too (perception plugins fill a per-frame game state, a state machine consumes it), but its code isn't licensed for use, so take the idea only.

3. **Learned scene classifier.** A small CNN on a downscaled full frame (about 96×72), exported to ONNX like the star model: gameplay, black, white, SM64 logo, file select, star select, course intro, death, Bowser arena, key cutscene, Grand Star, pause, X-Cam. Train it with colour, blur, scale, crop and compression augmentation. It would replace the per-user reset templates and most region tuning, and fade detection no longer depends on the HUD being visible. Around a millisecond per frame on CPU, by estimate; measure it.

4. **Recognise star digits instead of 120 classes.** The HUD font is a fixed sprite, so classifying 2 to 3 digits of 10 classes each (or matching templates) should generalise better than the 120-way star model. Decode the sequence against the route, since the count never goes down except on a reset, instead of the consecutive-prediction rules.

5. **Track the run as a hidden state.** Treat the run as a state (split index, in a level or not) and update beliefs from the per-frame evidence, with the route as the prior. A missed fadeout is then inferred from later evidence, and an impossible event, like a split seconds after the last one, is suppressed. The biggest conceptual change of these, and the one that justifies a rewrite.

6. **Labelled training data from an emulator.** An emulator with memory access (ares, Project64, Mupen) labels every frame for free: star count, health, death, level, transition state, key flags, Grand Star. Degrade the frames to look like capture cards, the Virtual Console and scaling, then fine-tune on the real recordings. fmichea's ASL autosplitter shows which values to read (animation, star count, stage, warp destination, global timer, camera mode) and what star grabs, key grabs and no-exit stars look like in them; take the addresses from the public n64decomp and STROOP maps, not from its code, which has no licence. Needs a way to get the ROM that's fine for the project, and there's a domain gap to measure. The lighter version is a labelling tool that pre-labels with today's heuristics so only corrections are typed, fed by clips from "Save the last 30 seconds of capture" above.

7. **Audio as a second signal.** The star and key fanfares, the death sound and Bowser's lines are distinctive, so matching their fingerprints gives sample-accurate events whatever the video quality. Many runners mute or don't route audio, it needs a new capture path on each platform, and it has to be synced with the video, so make it optional and fuse it with the video rather than depend on it.

8. **Normalise the capture before thresholds.** Estimate the black and white levels from the stream (limited against full range, Virtual Console letterboxing) and normalise before thresholding, so users don't have to tune black, white and colour-range thresholds for their capture.

Not worth it: an end-to-end video model (too little labelled data, hard to debug, and a wrong split costs a runner their run), and a rewrite in a faster language (nothing shows CPU is the limit; the timing problems are in the design).
